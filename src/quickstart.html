1. Prepare your environment

  • A Git repository and a change whose intended behavior you can judge.
  • Docker installed and running, with permission to create containers and build images.
  • Node.js 20 or later for the npm package. Standalone binaries do not need Node.
  • macOS or Linux. On Windows, use WSL 2 with Docker Desktop’s WSL integration.
  • A supported model-provider API key with provider billing enabled for BYOM, or an arnx Cloud account.

Supported test runners: Python with pytest; JavaScript / TypeScript with vitest, jest, node:test or bun; Rust with cargo-nextest (early). Single packages and multi-project repositories are supported, but setup is not guaranteed for every framework or dependency. arnx works best on single-package Python and TypeScript repositories. Tests that run only in a browser (Playwright, Cypress) are not run.

More languages are planned. Want to see more here? ↗

Rust is early and the least-tested runner. First setup compiles dependencies and test targets into the Docker image. It can take minutes on a small crate, much longer on a large workspace, and several GB of disk space. Generated integration tests exercise the crate’s public API. Try it, have fun, and open an issue with what worked or broke.

2. Bring your own keys, or use Cloud

Bring your own supported provider keys, or let arnx Cloud manage model access.

BYOM: your provider keys

ANTHROPIC_API_KEY alone is enough: every job then runs on Claude. arnx init writes model choices and budgets to .arnx/config.toml. A role whose key is missing is commented out, and Claude stands in.

The default harness: reviewer and setup on claude-sonnet-5-5, hunter on claude-haiku-5-5, second hunter on gpt-6.1-sol, second opinion on claude-sonnet-5-5 with gpt-6.1-sol as fallback. Keep keys in your shell or secret manager; never commit them.

Built-in providers are anthropic, openai and river. Z.ai ships as a table; DeepSeek, Kimi and OpenRouter ship commented out. Add any Messages- or Responses-compatible endpoint under [providers], with [prices]: a model without a price is not covered by the budget cap.

arnx prompts lists prompt keys. arnx prompts copy KEY writes that key to .arnx/prompts.toml for you to edit. Other keys keep following the defaults; no rebuild is needed. With arnx cloud its own prompts run.

arnx cloud

If you don’t want to manage multiple providers and API keys, use our arnx Cloud. New accounts start with $5 in Cloud credit. With the CLI installed, run the commands for your project from its repository directory.

Cloud / new arnx project
# New project
arnx init --cloud
arnx login
Cloud / existing arnx project 
# Switch an initialized project to Cloud
arnx cloud on --yes
arnx login

--yes records your consent to send code to arnx Cloud without an interactive prompt. Omit it to read and answer the prompt. arnx init --cloud selects Cloud but leaves consent to the first command that sends code, normally arnx review.

arnx login starts a GitHub device sign-in in your browser; complete it yourself. The CLI stores the token locally in ~/.config/arnx/credentials.json.

Check your account and configuration 
arnx credits
arnx doctor

arnx credits shows your balance. See Cloud credits. arnx doctor reports which models are active and checks your environment. {{CLOUD_DATA_FLOW}} Use arnx cloud off to switch back to your own keys. arnx logout removes the local sign-in token.

3. Let your favorite coding agent handle it

Don’t want to handle reviews in the terminal? No worries. Your favorite coding agent can take the wheel. arnx was built for that! Install the arnx skill so Claude Code, Codex and other agents that read Agent Skills can review and fix code after finishing a change. The page for coding agents has the whole loop.

Install in this repository 
arnx skill install

This writes .agents/skills/arnx/ (Codex and other Agent Skills agents) and .claude/skills/arnx/ (Claude Code), including the skill’s references. Commit these directories to share the workflow with your team. Alternatively, arnx skill install --user installs them under your home directory for use across repositories.

An identical installed copy is left unchanged. To replace an older or edited copy, inspect your changes first, then use arnx skill install --force (add --user for the user-wide copy).

The agent runs arnx review once, after saying what it may cost, then stops for you to run arnx triage and arnx accept. After that it runs arnx check, reads arnx prompt, fixes until check passes, runs each touched project’s full suite, and reports. Yours: init, logins, marks, answers, accept, whole-repository setup and commits. The agent never edits accepted tests.

In Claude Code: /plugin marketplace add arnx-dev/arnx, then /plugin install arnx@arnx. The skills CLI also finds it: npx skills add arnx-dev/arnx.

4. Run the workflow

With your own keys nothing is asked: the first send names the providers once. arnx cloud asks once per repository, and arnx cloud on asks too. Without a terminal, arnx exits 3 and sends nothing; arnx consent --cloud records consent (add --yes in scripts).

Run arnx init first. If already initialized, start at review. Lost? arnx next says where you are. Every command takes --json.

● ● ●CLI workflow / no sample output 
arnx init
arnx review
arnx triage
arnx accept
arnx prompt
# Make and inspect the product-code fix, then:
arnx check
  1. First review: sets up only the projects the change touches, proven by a quick look: the test listing, arnx’s one-line test and a few small test files. A later change in another project sets that one up then; one that fails is left to arnx setup --add. arnx setup is the optional whole-repository run with every suite: setup_usd defaults to $3.00 and setup_minutes to 40.
  2. Review: on a branch, the default includes commits since its base plus tracked uncommitted changes. Use arnx review --range A..B for an explicit span. On the default branch, it reviews tracked uncommitted work, or the last commit when clean. A documentation-only change is not reviewed (exit 0); arnx review --docs reviews it anyway.
  3. Accept: replace <id> with the review ID, or omit it for the latest review. Read the generated tests and use arnx triage to validate marks; some findings arrive pre-marked real. Acceptance can call a model to turn your answers into tests. arnx accept --no-answers skips that step.
  4. Check: fix production code, then rerun accepted tests with arnx check. No model inference is needed. Local Docker execution still consumes resources. Review and commit the fix, tests, and acceptance record.

Untracked files are excluded from setup and review by default in repositories with commits. --untracked or [review] untracked = true includes them. Exception: with no commits yet, non-ignored files form the initial change. Inspect .arnxignore and the reported scope before sending code. Secret filtering is not exhaustive.

Setup asks nothing and proves the environment by running it. It ends with “Worth a look”: tests failing today, tests skipped, commands that ignore errors, downloads from outside package registries, allowed secret-looking files and what no project tests. Failing tests are recorded per test in .arnx/baseline.json.

A changed .arnx/review.yaml is proven again before the next review, check or accept, and arnx says what changed. arnx approve only reruns that proof by hand.

Reviews are limited to 200 KB; use arnx review --range A..B for long branches. Lockfiles and generated files are not counted and not in the diff sent. Python, JavaScript/TypeScript and Rust only; no Windows build (use WSL 2). A backend whose tests need three or more services is listed as uncovered and must be set up by hand.

5. Keep the useful tests

arnx accept <id> keeps tests for findings marked real, then runs the accepted tests so you can see what still fails. Fix the code and run arnx check until they pass. Acceptance does not change your product code or commit anything.

Reviews live in .arnx/reviews/<id>/. Accepted tests live in .arnx/tests/, pinned by sha256 in .arnx/accepted-tests.json. Your own test run never collects them; only arnx check runs them, in a throwaway copy. Accepted tests are model-written code: read them first. arnx never edits your code or your tests.

arnx accept --move migrates tests from older versions.

Commit .arnx/config.toml, .arnx/review.yaml and .arnx/baseline.json. With the fix, commit .arnx/tests/, .arnx/accepted-tests.json and .arnx/answer-watch.json when there is one.

Review artifacts, run/setup files, and usage logs stay local and are ignored by Git. So does .arnx/precision.jsonl, your log of review marks. arnx init includes its ignore rule; arnx accept adds the rule to an older .arnx/.gitignore when missing. Ignore rules do not untrack files already in Git.

Accepted tests are pinned by their hashes in .arnx/accepted-tests.json. If a test or its record changes unexpectedly, arnx check stops with exit 4. arnx accept --again <id> restores the review’s tests, overwriting edits. For an intentional change you have reviewed, arnx accept --keep-edits records the current tests.

Costs and billing

With your own keys, you pay providers directly. Setup, review, and answer-to-test generation can incur model costs. Review your configured budgets; cost varies with model, change size, retries, and environment complexity. The CLI reports usage and writes .arnx/usage.jsonl. Reported case-study costs are observations, not prices or promises.

Expect a few cents to a few dollars per review. Our own reviews ranged from $0.17 to $3.19; the public checkout demo cost $0.13 with setup. Set review_usd under [budget] to control spending (default $3.00); the review stops writing tests when it reaches the cap and reports that it did.

arnx check and arnx check --review do not call models. {{CLOUD_DESCRIPTION}} How Cloud credit is billed.

arnx check --review remains the fix-first option: run a review’s confirmed tests before accepting. arnx remove lists what arnx added; arnx env prune removes old test images.

Common failures

Cloud needs sign-in, consent, or credits
Run arnx login for missing or expired authentication. For missing Cloud consent, run arnx consent --cloud, or arnx consent --cloud --yes to explicitly agree without a prompt. Check arnx credits if your balance cannot cover a review. arnx next names the next step.
Docker or a provider key is missing
Run arnx doctor. Start Docker, check daemon permissions, and verify the configured key variable without posting its value.
Image build or dependency download fails
Read the setup log and proposed commands. Check registry connectivity and project dependency versions. Image builds need network access.
Setup cannot establish a working suite
Check the test command, fixtures, service readiness, and excluded projects. An incomplete environment is not a clean review. arnx next reports the current state.
A review is interrupted
Inspect its report and use arnx review --resume when appropriate. An incomplete run is not evidence that the change has no bugs.
Check says a test changed
Exit 4 indicates an edited or missing accepted file or record. Restore unintended changes. Use arnx accept --keep-edits only after deliberately reviewing a test change.
Nothing was accepted
arnx check exits 3 when there are no accepted tests. Validate findings and run accept first.

Review exit codes: 0 fine (confirmed findings are worth a look and do not fail the run; CI reads result in arnx review --json), 1 a finding the second opinion could not check, 2 incomplete, 3 setup needed. Check exit codes: 0 passed, 1 failed, 2 some tests did not report, are unproven or were not run, 3 nothing accepted, 4 accepted-test integrity changed. A 0 is not a correctness guarantee.
