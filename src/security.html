Trust / Security

Know what runs.
Know what leaves.

Docker execution and external model inference are separate.

Code and provider access

The CLI can submit the selected diff, files read during investigation, generated tests, and test output to configured providers. With your own keys, inference requests go directly to those providers under your account. Their data handling and billing terms apply.

Values that may be secrets are replaced by stand-ins: fakes of the same shape in the snapshot, used by the tests too. A password in a connection address counts. A private key is a fake in the sandbox and [private key] to a model; its file is still reviewed. [review] stand_ins = false turns stand-ins off. The filter is a heuristic: extend .arnxignore for anything else private.

When setup needs a file excluded by .arnxignore, it may copy it into the sandbox as sandbox_only. It is scrubbed the same way, never sent to a model, and arnx says so. Test output may still quote it. arnx allow-secret PATH allows pinned key-shaped test fixtures, not real credentials.

Setup and review exclude untracked files by default when the repository has commits. --untracked or [review] untracked = true opts them in. With no commits, non-ignored files form the initial change. Stage and review files deliberately.

Docker boundaries

Tests execute against a copy of the repository. Test containers have CPU, memory, and process limits; capabilities are dropped and no-new-privileges is set. Runs use no network or an internal network for configured services. The test environment receives explicitly configured variables rather than the host’s entire environment.

Image builds have network access for dependency installation. Install steps are written by the setup agent. Downloads from outside package registries are listed under “Worth a look”. Inspect service images, test code and declared variables too. Docker shares the host kernel; it is not a perfect boundary for hostile code. The CLI itself also needs access to your repository, provider credentials, and Docker daemon.

Retained tests and reports

Review reports stay under .arnx/. Accepted tests live in .arnx/tests/, pinned by sha256 in .arnx/accepted-tests.json. Your own test run never collects them. Only arnx check runs them, in a throwaway copy. Read this model-written code before committing it. arnx never edits your code or your tests.

Consent

With your own keys nothing is asked; the first send names the providers once. arnx cloud asks once per repository, and arnx cloud on asks too. Without a terminal, arnx exits 3 and sends nothing. Use arnx consent --cloud, with --yes in scripts, to record it.

Private deployment requirements

For Enterprise, contact us to discuss your required deployment location, model access, data retention, and support. Deployment and data boundaries depend on the agreed setup; using local Docker alone does not keep inference requests local. Discuss Enterprise requirements.

Report a security issue privately

Email info@arnx.dev with “arnx security report” in the subject. See the repository security policy. Include affected versions, impact, and a minimal reproduction you can safely share. Do not put credentials or exploitable private details in a public issue. We do not currently publish a guaranteed response time or a bug-bounty program.
