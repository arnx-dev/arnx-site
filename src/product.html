Open-source AI code review

Your agent writes the code. arnx checks the behavior.

A CLI for investigating changes with executable evidence.

arnx reads a code change, investigates suspected bugs, and generates and runs targeted tests in Docker. A failure is evidence to inspect. You decide whether the behavior is wrong and which tests to keep.

From a change to a regression check

arnx init → arnx review → arnx triage → arnx accept → arnx prompt → arnx check. Init is required. The first review sets up only the projects the change touches in a few minutes (it stops at 10), with no separate setup step. arnx setup optionally runs the whole repository’s suites.

You or your coding agent change the production code. arnx prompt provides a handoff; arnx check runs accepted tests on the working tree, without new model calls.

What a finding means

arnx runs each test 3 times, reruns failures on the code before the change, and has a second model confirm or dispute it. A failing test shows an assertion fails, not that the code is wrong. Model replies vary: two reviews of one change can differ.

Before/after outcomes are regression, pre-existing, new-code, changed or unknown. Only regression is evidence about the change: the test passes before and fails after, if its expectation is right.

Findings with one cause are grouped into an issue, most severe first, explained as input, actual, expected and why it matters. Issues backed by a confirmed test come pre-marked real; change what you disagree with. Marks are real, intended, noise or rewrite.

Tests that pass after the change but fail before it appear under “The change fixes”. Changed code no test touched is listed by name, and the review says “partly covered”. A passing check covers only the accepted tests.

arnx reviewing its own arnx remove command

From the README’s recorded review, before 0.1: a test for paths escaping the repository, followed by the report excerpt. Quoted exactly. 

test("S2 accepted-test paths escaping the repository are never deleted", async () => {
  const { base, repo, env } = setup();
  const victim = join(base, "victim.txt");
  put(victim, "keep me");
  put(join(repo, ".arnx", "accepted-tests.json"), record({ "../victim.txt": {} }));
  const cli = new Cli({ cwd: repo, env });
  await withDocker("/nonexistent/docker", () => cli.run("remove", "--yes", "--tests"));
  expect(existsSync(victim)).toBe(true);
});
### Issue 1 · remove --yes can delete files outside the repository
- Actual: In S2, `../victim.txt` outside the repository was deleted. …
- Failing tests: F2, F4

### F2 · regression · confirmed by the second opinion
- Failure: `expect(received).toBe(expected)`
- Before the change (regression): passes on the code before the change (3 runs): the change broke it
- Second opinion: planRemove takes accepted-tests.json keys verbatim and applyRemove rmSync's join(repo, p), …

The test failed in all 3 runs, passed before the change, and the second model agreed. We marked it real, kept it with arnx accept, fixed the code from the fix prompt and saw it pass in arnx check. Not every finding is like this one: in our own reviews, some confirmed issues tested behaviour we intended.

What a check means

A passing check means the accepted tests passed in that environment. It does not establish that the entire change is correct. Read the review’s coverage gaps, untested files, unresolved questions, and incomplete runs.

Generated tests can be wrong or fragile. Developer validation matters even when a failure repeats and another model agrees. Accepted files are pinned so editing a test to make it pass is detected; inspect deliberate test changes before accepting them again.

Accepted tests live in .arnx/tests/, pinned by sha256 in .arnx/accepted-tests.json. Your own test run never collects them; only arnx check runs them in a throwaway copy. Read this model-written code first. arnx never edits your code or your tests.

Local execution, external inference

Tests run in local Docker containers. Diffs, selected files, generated tests, and test output can go to model providers. Bring your own supported API keys; your coding-agent subscription should not be assumed to cover these calls.

Where it fits

Run the CLI before opening a pull request or while reviewing a change. It complements your existing tests and human review. Current runners cover Python/pytest, JavaScript and TypeScript with vitest, jest, node:test or bun, and Rust with cargo-nextest (early). Environment setup still needs validation for your repository.

Rust is the least-tested runner. First setup is slow because the image compiles dependencies and test targets, and it can take several GB. Try it on your crate, swap models, and tell us what breaks.
