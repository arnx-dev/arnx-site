Case study / Hummingbot

A status result landed on the wrong order.

One fix sent upstream. Other findings the maintainers had already fixed themselves.

Hummingbot is an open-source trading bot framework. In October 2026 arnx reviewed commits from a large gateway change that had merged in August. This page keeps three things apart:

  • A finding we sent upstream. A bug in how order statuses are paired with orders, with arnx's test and a fix, as hummingbot/hummingbot#8508. On 2026-11-12 it is open, with no maintainer review yet.
  • Findings the maintainers had already fixed. A review of an earlier commit confirmed issues that later commits in the same upstream pull request, #8431, had fixed two months before arnx ran.
  • What arnx did not do. It caused none of the fixes in #8431. Those were the maintainers' own work.

1. Repository and reviewed commit

hummingbot/hummingbot. Upstream pull request #8431 merged on 2026-08-26 with 47 commits. We picked single commits from it to review after the fact:

  • 9f6a2e8ba (2026-08-13), which bounds pending-transaction polling with a deadline: 3 files, 101 lines added. This review produced the finding we sent upstream.
  • 056912818 (2026-08-19), which reconciles broadcast transactions before retrying. This review produced the findings the maintainers had already fixed.

2. Expected behavior

GatewayBase.update_order_status polls the status of each tracked order's transaction. Each result should be applied to the order whose transaction it describes. An order whose hash lookup failed should be skipped for that round and nothing else.

3. Actual behavior

The method looks up each order's transaction hash, drops the lookups that failed, and asks for the status of the remaining hashes. It then paired those results with the full order list by position:

gateway_base.py, before the fix 
for tracked_order, tx_details in zip(tracked_orders, update_results):

Once one order is dropped, every result after it lands on the wrong order. An order with no transaction yet can receive another order's status, and the order that does have a hash gets no status that round.

4. Suspected defect

Before any test ran, the reviewer suspected: The status results are zipped against tracked_orders, but tx_hash_list drops orders whose exchange_order_id raised an exception. The results shift onto the wrong orders. The filter that drops failed lookups predates the reviewed commit. The commit added a new branch that counts not-found results, and that branch inherited the misalignment.

5. Generated test

Written by arnx, as accepted 
def test_s4_s5_not_found_applied_to_correct_order(loop):
    c = make_connector(("A", "B"))
    a = c._order_tracker.fetch_tracked_order("A")
    b = c._order_tracker.fetch_tracked_order("B")
    c._set_current_timestamp(T0 + c.TX_NOT_FOUND_DEADLINE + 1)
    hb = "1" * 88

    async def boom():
        raise RuntimeError("no hash")

    a.get_exchange_order_id = boom
    poll(loop, c, [a, b], {hb: -2})
    records = c._order_tracker._order_not_found_records
    assert records["A"] == 0
    assert records["B"] == 1

Order A's hash lookup fails. Order B's transaction is not found. The miss should count against B only.

arnx found this twice. The first review, on 2026-10-23 with arnx 0.1.1, ran 13 tests in 13 minutes 32 seconds for $0.43. A second review of the same commit on 2026-11-03, with arnx 0.1.7 and arnx Cloud, took 11 minutes 29 seconds and was billed $0.63. The quote above is from the second. These numbers come from our local review records, not from a public page.

The before/after check could not call it a regression. The test uses a constant the commit adds, so there was nothing to compare on the older code. We then reproduced the misalignment by hand on the repository's head at the time.

7. Correction

The fix keeps each order paired with its own hash and zips the results with the orders that were actually queried. Orders whose lookup failed are still skipped for that round, as before. A coding agent wrote the fix from arnx's fix prompt. The test in the pull request is arnx's accepted test, trimmed to the one case. The owner of arnx opened the pull request.

8. Verification result

From the pull request: on the development branch the new test fails with assert 1 == 0; with the fix A has 0 misses and B has 1. The gateway connector and executor tests report 572 passed without the fix and 573 with it. The full suite with the fix, minus three paths that depend on the environment, reported 8,643 passed.

On GitHub on 2026-11-12: open since 2026-10-23, no maintainer review, not merged. Whether the maintainers consider it a bug worth fixing is not yet known.

10. Limitations and observations

  • The pull request is unreviewed. Until a maintainer answers, the pairing bug is our claim, backed by a failing test and a reproduction, not a confirmed defect.
  • The review of 056912818 missed one. The same upstream commit that fixed the fee figures also removed a leftover call that raised on every failed request. arnx did not report it.
  • Hindsight is easier than review at merge time. We chose commits knowing the work had merged. A review run in August would have had the same code, but we did not run one, so this is not evidence that arnx would have caught these before the developer did.
  • In the first review of 9f6a2e8ba the second opinion disputed four other findings. We agreed with all four disputes.
  • The repository already runs an automated pull request reviewer. This page does not compare the two.
  • Reviews of three other commits from the same work found nothing we would send upstream. One reported a failure that the real client cannot reach; another tested behavior the commit message describes as intended.
